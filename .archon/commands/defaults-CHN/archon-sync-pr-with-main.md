# 将 PR 与 Main 分支同步

---

## 任务目标

确保 PR 分支在审查前与最新的 main 分支保持同步。必要时进行变基（rebase），解决可能出现的冲突。当无需操作时，此步骤静默通过。

**输出产物**：`$ARTIFACTS_DIR/review/sync-report.md`（仅在发生变基/冲突时生成）

---

## 阶段一：检查 -- 判断是否需要同步

### 1.1 从注册文件获取 PR 编号

```bash
PR_NUMBER=$(cat $ARTIFACTS_DIR/.pr-number)
```

### 1.2 读取范围

```bash
cat $ARTIFACTS_DIR/review/scope.md
```

获取分支名称：`PR_HEAD` 和 `PR_BASE`。

### 1.3 拉取并切换 PR 分支

```bash
git fetch origin $PR_BASE
git fetch origin $PR_HEAD
```

确认你当前在 PR 的分支（`$PR_HEAD`）上。如果不是，请切换：

```bash
git checkout $PR_HEAD
```

### 1.4 检查是否落后

```bash
# 统计 PR 分支落后 main 的提交数
BEHIND=$(git rev-list --count HEAD..origin/$PR_BASE)
echo "Behind by: $BEHIND commits"
```

**决策：**

| 落后提交数 | 操作 |
|-----------|------|
| 0 | 跳过 -- 已经是最新 |
| 1+ | 需要变基 |

**如果已经是最新：**
```markdown
分支已与 `{base}` 同步。无需同步操作。
```
**提前结束 -- 不创建产物。**

**阶段一检查点：**
- [ ] 已识别 PR 编号
- [ ] 已拉取分支
- [ ] 已确定落后提交数

---

## 阶段二：变基 -- 与 Main 同步

### 2.1 尝试变基

```bash
git rebase origin/$PR_BASE
```

**可能的结果：**

| 结果 | 下一步 |
|------|--------|
| 成功（无冲突） | 进入阶段四（验证） |
| 有冲突 | 进入阶段三（解决冲突） |
| 其他错误 | 报告并中止 |

### 2.2 检查冲突

```bash
# 如果变基暂停，检查冲突
git diff --name-only --diff-filter=U
```

如果列出了文件 --> 存在冲突，进入阶段三。
如果为空 --> 变基成功，进入阶段四。

**阶段二检查点：**
- [ ] 已尝试变基
- [ ] 已确定冲突状态

---

## 阶段三：解决冲突（如有）

### 3.1 识别冲突文件

```bash
git diff --name-only --diff-filter=U
```

### 3.2 分析每个冲突

对每个冲突文件：

```bash
# 显示冲突标记
cat {file} | grep -A 10 -B 2 "<<<<<<<"
```

**分类：**
- **简单**：一方添加/修改，另一方未触碰 --> 自动解决
- **复杂**：双方修改了相同的行 --> 需要判断

### 3.3 自动解决简单冲突

对于意图明确的冲突：
- 双方添加了不同内容 --> 保留两者
- 一方更新，另一方未动 --> 保留更新
- 导入的新增 --> 合并两者

```bash
# 编辑文件解决冲突
# 然后暂存
git add {file}
```

### 3.4 解决复杂冲突

对于需要判断的冲突：

1. 阅读两个版本以理解意图
2. 根据以下因素选择解决方案：
   - PR 意图（本次变更要做什么？）
   - 基础分支更新（main 中改了什么？）
   - 代码正确性
3. 应用解决方案并暂存

```bash
git add {file}
```

### 3.5 继续变基

```bash
git rebase --continue
```

如果更多提交存在冲突，重复此过程。

**阶段三检查点：**
- [ ] 已识别所有冲突
- [ ] 已自动解决简单冲突
- [ ] 已基于推理解决复杂冲突
- [ ] 变基已完成

---

## 阶段四：验证 -- 确认同步结果

### 4.1 检查无残留冲突标记

```bash
git diff --check
```

应返回空结果。

### 4.2 类型检查

```bash
bun run type-check
```

### 4.3 运行测试

```bash
bun test
```

### 4.4 代码检查

```bash
bun run lint
```

**如果任何步骤失败**：在继续之前修复问题。

**阶段四检查点：**
- [ ] 无冲突标记
- [ ] 类型检查通过
- [ ] 测试通过
- [ ] 代码检查通过

---

## 阶段五：推送 -- 更新远程

### 5.1 确认分支并推送

确认你在 `$PR_HEAD` 上，然后推送：

```bash
git push --force-with-lease origin $PR_HEAD
```

**注意**：`--force-with-lease` 更安全 -- 如果其他人已推送，则会失败。

### 5.2 验证推送

```bash
git log origin/$PR_HEAD --oneline -3
```

确认本地与远程一致。

**阶段五检查点：**
- [ ] 分支已推送
- [ ] 远程已更新

---

## 阶段六：报告 -- 记录同步情况（仅在发生变基/冲突时）

### 6.1 创建同步产物

写入 `$ARTIFACTS_DIR/review/sync-report.md`：

```markdown
# 同步报告：PR #{number}

**日期**：{ISO 时间戳}
**操作**：变基到 `{base}`

---

## 概要

- **变基提交数**：{N}
- **解决冲突数**：{M}（涉及 {X} 个文件）
- **状态**：✅ 同步成功

---

## 已解决的冲突

{如果解决了冲突：}

### `{file}`

**类型**：{简单 | 复杂}
**解决方案**：{描述}

```{language}
{解决后的代码}
```

---

{如果没有冲突：}

变基过程中未遇到冲突。

---

## 验证结果

| 检查项 | 状态 |
|--------|------|
| 类型检查 | ✅ |
| 测试 | ✅ |
| 代码检查 | ✅ |

---

## Git 状态

**变基前**：{旧 HEAD 提交}

- **时间戳**：{ISO 时间戳}
```

### 6.2 更新范围产物

追加到 `$ARTIFACTS_DIR/review/scope.md`：

```markdown
---

## 同步状态

**同步时间**：{ISO 时间戳}
**变基到**：`{base}` 的 {commit} 提交
**解决冲突数**：{N}
```

**阶段六检查点：**
- [ ] 已创建同步产物（如果执行了操作）
- [ ] 已更新范围产物

---

## 阶段七：输出 -- 报告状态

### 如果执行了变基（有或无冲突）：

```markdown
## ✅ PR 已与 Main 同步

**分支**：`{head}` 已变基到 `{base}`
**变基提交数**：{N}
**解决冲突数**：{M}

验证结果：✅ 类型检查 | ✅ 测试 | ✅ 代码检查

正在进入并行审查...
```

### 如果已是最新：

```markdown
## ✅ PR 已是最新

分支 `{head}` 与 `{base}` 一致。无需同步。

正在进入并行审查...
```

### 如果同步失败：

```markdown
## ❌ 同步失败

**错误**：{描述}

**需要操作**：需要手动干预。

```bash
# 中止失败的变基
git rebase --abort
```

**建议**：手动解决冲突后重新触发审查。
```

---

## 错误处理

### 变基完全失败

```bash
git rebase --abort
```

报告失败并附上具体错误。

### 推送被拒绝

如果 `--force-with-lease` 失败：
1. 其他人已推送到该分支
2. 拉取并重新尝试变基
3. 或报告以进行手动处理

### 验证失败

如果变基后类型检查/测试失败：
1. 调查哪些变更导致了问题
2. 尝试修复
3. 如果无法修复，中止并报告

---

## 成功标准

- **已同步**：分支已与基础分支同步（或已是最新）
- **无冲突**：所有冲突已解决（如果存在的话）
- **验证通过**：类型检查、测试、代码检查全部通过
- **已推送**：远程分支已更新（如果执行了变基）
