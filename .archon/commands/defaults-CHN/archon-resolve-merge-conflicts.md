# 解决合并冲突

**输入**: $ARGUMENTS

---

## 你的任务

分析 PR 中的合并冲突，在意图明确时自动解决简单冲突，为复杂冲突提供选项建议，并推送解决方案。

---

## 阶段 1：识别 — 获取 PR 和冲突信息

### 1.1 解析输入

**检查输入格式：**
- 数字（`123`、`#123`）→ GitHub PR 编号
- URL（`https://github.com/...`）→ 提取 PR 编号
- 为空 → 检查当前分支是否有未关闭的 PR

```bash
gh pr view {number} --json number,title,headRefName,baseRefName,mergeable,mergeStateStatus
```

### 1.2 确认冲突存在

```bash
gh pr view {number} --json mergeable,mergeStateStatus --jq '.mergeable, .mergeStateStatus'
```

| 状态 | 操作 |
|------|------|
| `CONFLICTING` | 继续解决 |
| `MERGEABLE` | 报告"无冲突需要解决"并退出 |
| `UNKNOWN` | 等待重试，或谨慎继续 |

**若无冲突：**
```markdown
## ✅ 无冲突

PR #{number} 没有合并冲突，可以进入审查/合并流程。
```
**若无冲突则退出。**

### 1.3 设置本地分支

```bash
# 获取分支信息
PR_HEAD=$(gh pr view {number} --json headRefName --jq '.headRefName')
PR_BASE=$(gh pr view {number} --json baseRefName --jq '.baseRefName')

# 拉取最新代码
git fetch origin $PR_BASE
git fetch origin $PR_HEAD

# 切换到 PR 分支
git checkout $PR_HEAD
git pull origin $PR_HEAD
```

**阶段 1 检查点：**
- [ ] 已识别存在冲突的 PR
- [ ] 分支已拉取
- [ ] 已切换到 PR 分支

---

## 阶段 2：分析 — 理解冲突

### 2.1 尝试变基以暴露冲突

```bash
git rebase origin/$PR_BASE
```

这将停在第一个冲突处。注意输出信息。

### 2.2 识别冲突文件

```bash
git diff --name-only --diff-filter=U
```

列出所有有冲突的文件。

### 2.3 分析每个冲突

对每个冲突文件：

```bash
# 显示冲突标记
git diff --check
cat {file} | grep -A 10 -B 2 "<<<<<<<"
```

**对每个冲突进行分类：**

| 类型 | 描述 | 可自动解决？ |
|------|------|-------------|
| **简单添加** | 一方添加了内容，另一方未修改该区域 | ✅ 可以 |
| **简单删除** | 一方删除了内容，另一方未修改 | ⚠️ 视情况（需确认意图） |
| **不同区域** | 双方都修改了但涉及不同行 | ✅ 可以 |
| **相同行** | 双方修改了完全相同的行 | ❌ 需要决策 |
| **结构性** | 文件被移动/重命名且被修改 | ❌ 需要决策 |

### 2.4 阅读两个版本

对于复杂冲突，理解双方的意图：

```bash
# 显示基础版本（共同祖先）
git show :1:{file} 2>/dev/null || echo "文件在基础版本中不存在"

# 显示"我们的"版本（HEAD/当前分支）
git show :2:{file}

# 显示"他们的"版本（来自基础分支的传入变更）
git show :3:{file}
```

**阶段 2 检查点：**
- [ ] 所有冲突文件已识别
- [ ] 每个冲突已分类
- [ ] 双方的意图已理解

---

## 阶段 3：解决 — 修复冲突

### 3.1 自动解决简单冲突

对于意图明确的冲突：

```bash
# 对每个可自动解决的文件
# 编辑以保留双方变更（如果双方都是添加内容）
# 或根据意图保留适当的一侧
```

**自动解决规则：**
1. **双方添加了不同内容**：保留双方的添加
2. **一方更新，另一方未触碰**：保留更新
3. **导入添加**：合并两个导入列表
4. **注释变更**：保留信息更丰富的版本

### 3.2 为复杂冲突提供选项

对于需要人工决策的冲突：

```markdown
## 文件 `{file}` 中的冲突

**第 {start}-{end} 行**

### 选项 A：保留 PR 变更（HEAD）
```{language}
{PR 分支的代码}
```

**作用**：{PR 意图的解释}

### 选项 B：保留基础分支变更
```{language}
{基础分支的代码}
```

**作用**：{基础分支意图的解释}

### 选项 C：合并双方（若兼容则推荐）
```{language}
{可能的合并版本}
```

**理由**：{为什么这种合并是合理的}

### 选项 D：需要自定义解决
变更不兼容，需人工审查。

---

**推荐**：选项 {X}

**理由**：{基于以下因素为何选择此选项：
- 代码功能
- 从标题/描述推断的 PR 意图
- 哪个变更新近/更完整
- 对其他代码的影响}
```

### 3.3 应用解决方案

对每个冲突：

1. **若可自动解决**：应用解决方案
2. **若需决策**：使用推荐选项（或在不明确时询问用户）

```bash
# 编辑每个文件后
git add {file}
```

### 3.4 继续变基

```bash
# 解决当前提交的所有冲突后
git rebase --continue
```

对后续有冲突的提交重复此过程。

**阶段 3 检查点：**
- [ ] 所有简单冲突已自动解决
- [ ] 复杂冲突已解决并记录理由
- [ ] 所有文件已暂存
- [ ] 变基已完成

---

## 阶段 4：验证 — 确认解决方案

### 4.1 检查是否还有剩余冲突

```bash
git diff --check
```

应返回空（没有残留的冲突标记）。

### 4.2 验证代码编译

```bash
bun run type-check
```

如果存在与解决方案相关的类型错误，进行修复。

### 4.3 运行测试

```bash
bun test
```

如果因解决方案导致测试失败，调查并修复。

### 4.4 Lint 检查

```bash
bun run lint
```

修复所有 lint 问题。

**阶段 4 检查点：**
- [ ] 无残留冲突标记
- [ ] 类型检查通过
- [ ] 测试通过
- [ ] Lint 通过

---

## 阶段 5：推送 — 更新 PR

### 5.1 强制推送已解决的分支

```bash
git push --force-with-lease origin $PR_HEAD
```

**注意**：`--force-with-lease` 比 `--force` 更安全，如果其他人有推送会失败。

### 5.2 确认 PR 现在可合并

```bash
gh pr view {number} --json mergeable,mergeStateStatus
```

应显示 `MERGEABLE`。

**阶段 5 检查点：**
- [ ] 分支已成功推送
- [ ] PR 显示为可合并

---

## 错误处理

### 变基中途失败

如果变基在某个无法解决的提交上失败：

```bash
# 检查状态
git status

# 如果确实无法继续，中止并报告
git rebase --abort
```

报告失败详情，包括涉及的提交和原因。

### 推送失败

如果 `--force-with-lease` 失败（其他人有推送）：

1. 拉取最新代码
2. 重新分析冲突
3. 从头开始

### 解决后验证失败

如果解决后类型检查/测试失败：

1. 调查是哪个解决方案导致了问题
2. 尝试替代解决方案
3. 如果无法解决，报告并建议人工审查

---

## 成功标准

- **冲突已识别**：所有冲突文件已找到
- **冲突已解决**：所有冲突已解决（自动或手动）
- **验证通过**：类型检查、测试、Lint 全部通过
- **分支已推送**：PR 分支已更新为解决方案
- **PR 可合并**：GitHub 显示 PR 为可合并状态
- **已记录**：解决方案产物和 GitHub 评论已创建
