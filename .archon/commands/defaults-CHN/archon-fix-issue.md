# 修复 Issue

**输入**: $ARGUMENTS

---

## 你的任务

执行来自 `/investigate-issue` 的实现计划:

1. 加载并验证产物
2. 确保 git 状态正确
3. 发现并安装工作区中的依赖
4. 完全按照规格实施变更
5. 运行验证
6. 提交变更
7. 编写实现报告

**黄金法则**: 遵循产物。如果某些内容看起来不对，先验证——不要静默偏离。

---

## 阶段 1: 加载 - 获取产物

### 1.1 查找调查产物

查找上一步生成的调查产物:

```bash
# 在工作流运行目录中检查产物
ls $ARTIFACTS_DIR/investigation.md
```

**如果输入是特定路径**，直接使用该路径。

### 1.2 加载并解析产物

```bash
cat {artifact-path}
```

**从产物中提取:**
- Issue 编号和标题
- 类型（BUG/ENHANCEMENT 等）
- 需要修改的文件（含行号）
- 实施步骤
- 验证命令
- 需要添加的测试用例

### 1.3 验证产物是否存在

**如果未找到产物:**
```
❌ 在 $ARTIFACTS_DIR/investigation.md 处未找到调查产物

请先运行 `/investigate-issue {number}` 创建实现计划。
```

**阶段 1 检查点:**
- [ ] 产物已找到并加载
- [ ] 关键章节已解析（文件、步骤、验证）
- [ ] Issue 编号已提取（如适用）

---

## 阶段 2: 验证 - 合理性检查

### 2.1 验证计划准确性

对于产物中提到的每个文件:
- 阅读实际的当前代码
- 与产物预期进行对比
- 检查"当前代码"片段是否与实际一致

**如果检测到显著偏差:**
```
⚠️ 代码自调查以来已发生变化:

文件: src/x.ts:45
- 产物预期: {代码片段}
- 实际代码: {不同的代码片段}

选项:
1. 重新运行 /investigate-issue 获取最新分析
2. 谨慎进行手动调整
```

### 2.2 确认方案合理

自问:
- 提议的修复是否真正解决了根本原因？
- 方案是否存在明显问题？
- 是否有变化导致计划失效？

**如果计划看起来不对:**
- 停止
- 解释问题所在
- 建议重新调查

**阶段 2 检查点:**
- [ ] 产物与当前代码库状态匹配
- [ ] 方案仍然合理
- [ ] 未发现阻碍性问题

---

## 阶段 3: Git 检查 - 确保正确状态

### 3.1 检查当前 Git 状态

```bash
# 当前在哪个分支？
git branch --show-current

# 是否在工作区中？
git rev-parse --show-toplevel
git worktree list

# 工作目录是否干净？
git status --porcelain

# 是否与远程同步？
git fetch origin
git status
```

### 3.2 决策树

```text
┌─ 在工作区中？
│  └─ 是 → 保持当前分支不变。不要切换分支。不要创建新分支。
│           隔离系统已设置好正确的分支；任何偏离都会操作错误的代码。
│           日志: "使用工作区 {path}，分支 {branch}"
│
├─ 在 $BASE_BRANCH 上？（main、master 或配置的基准分支）
│  └─ 问: 工作目录是否干净？
│     ├─ 是 → 创建分支: fix/issue-{number}-{slug}
│     │        git checkout -b fix/issue-{number}-{slug}
│     │        （仅在非工作区时适用 — 例如手动 CLI 使用）
│     └─ 否  → 停止: "$BASE_BRANCH 上有未提交的变更。
│              请先提交或暂存后再继续。"
│
├─ 在其他分支上？
│  └─ 保持不变（假设它是为此工作设置的）。
│     不要切换到其他分支（例如 `git branch` 显示但
│     未当前检出的分支）。
│     如果分支名不包含 issue 编号:
│       警告: "分支 '{name}' 可能不是为 issue #{number} 创建的"
│
└─ 工作目录有未提交变更？
   └─ 停止: "有未提交的变更。请先提交或暂存。"
```

### 3.3 确保代码是最新的

```bash
# 如果分支跟踪远程
git pull --rebase origin $BASE_BRANCH 2>/dev/null || git pull origin $BASE_BRANCH
```

**阶段 3 检查点:**
- [ ] Git 状态干净且正确
- [ ] 在适当的分支上（新建或已有）
- [ ] 与基准分支同步

## 阶段 4: 依赖 - 发现并安装

### 4.1 检测安装命令

检查工作区中的锁文件/配置文件并选择安装命令:

- `package.json` + `bun.lock` → `bun install`
- `package.json` + `package-lock.json` → `npm install`
- `package.json` + `yarn.lock` → `yarn install`
- `package.json` + `pnpm-lock.yaml` → `pnpm install`
- `requirements.txt` → `pip install -r requirements.txt`
- `pyproject.toml` + `poetry.lock` → `poetry install`
- `Cargo.toml` → `cargo build`
- `go.mod` → `go mod download`

### 4.2 执行安装

在进行任何验证或测试之前，从工作区根目录运行选定的安装命令。

### 4.3 安装失败处理

如果安装失败，停止并报告错误。不要在缺少依赖的情况下继续验证。

**阶段 4 检查点:**
- [ ] 安装命令已发现
- [ ] 依赖已成功安装

---

## 阶段 5: 实施 - 执行变更

### 5.1 执行每个步骤

对产物实施计划中的每个步骤:

1. **阅读目标文件** - 理解当前状态
2. **执行变更** - 完全按照规格
3. **验证类型编译** - `bun run type-check`

### 5.2 实施规则

**要做:**
- 按顺序遵循产物步骤
- 严格匹配现有代码风格
- 从"要遵循的模式"章节复制模式
- 按规格添加测试

**不要做:**
- 重构无关代码
- 添加计划外的"改进"
- 修改未触及行的格式
- 在未记录的情况下偏离产物

### 5.3 处理每种文件类型

**对于需要更新的文件:**
- 阅读当前内容
- 找到提到的确切行
- 执行指定的变更
- 保留周围代码不变

**对于需要创建的文件:**
- 使用产物中的模式
- 遵循现有文件结构约定
- 包含所有指定内容

**对于测试文件:**
- 按规格添加测试用例
- 遵循现有测试模式
- 确保测试确实测试了修复内容

### 5.4 记录偏差

如果必须偏离产物:
- 记录变更内容和原因
- 在实现报告中注明

**阶段 5 检查点:**
- [ ] 产物中的所有步骤已执行
- [ ] 每次变更后类型编译通过
- [ ] 测试已按规格添加
- [ ] 任何偏差已记录

### 6.3 手动验证（如有指定）

执行产物中的任何手动验证步骤。

**阶段 6 检查点:**

- [ ] 手动验证完成（如适用）

## 阶段 7: 提交 - 保存变更

### 7.1 暂存变更

仅暂存你实际编辑的文件——切勿使用 `git add -A`、`git add .` 或 `git add -u`。逐个列出文件名:

```bash
git add path/to/file1 path/to/file2 ...
git status --porcelain  # 验证没有临时/审查/PR 正文文件被暂存
```

**切勿暂存:**

- `.pr-body.md`、`pr-body.md`、`*.scratch.md`、`*.tmp.md`
- 仓库根目录下的 `review/`、`*-report.md`
- `$ARTIFACTS_DIR` 下的任何内容

### 7.2 编写提交信息

**格式:**
```
Fix: {简要描述} (#{issue-number})

{产物中的问题描述 - 1-2 句话}

Changes:
- {产物中的变更 1}
- {产物中的变更 2}
- 添加了 {场景} 的测试

Fixes #{issue-number}
```

**提交:**
```bash
git commit -m "$(cat <<'EOF'
Fix: {标题} (#{number})

{问题描述}

Changes:
- {变更 1}
- {变更 2}

Fixes #{number}
EOF
)"
```

**阶段 7 检查点:**
- [ ] 所有变更已提交
- [ ] 提交信息引用了 issue

## 边界情况处理

### 产物已过时
- 警告用户代码偏差
- 建议重新运行 `/investigate-issue`
- 如果变更较小，可以谨慎继续

### 实施后测试失败
- 调试失败原因
- 修复代码（不修复测试，除非测试本身有误）
- 重新运行验证
- 在实现报告中注明额外修复

### rebase 时的合并冲突
- 解决冲突
- 重新运行完整验证
- 在实现报告中注明冲突解决

### 已在某个分支上有变更
- 使用现有分支
- 如果分支名与 issue 不匹配则发出警告
- 不要创建新分支

### 在工作区中
- 保持原样使用
- 假设它是为此目的创建的
- 记录正在使用工作区

## 成功标准

- **PLAN_EXECUTED**: 所有调查步骤已完成
- **VALIDATION_PASSED**: 所有检查通过
- **CHANGES_COMMITTED**: 所有变更已提交到分支
- **IMPLEMENTATION_ARTIFACT**: 已写入 $ARTIFACTS_DIR/
- **READY_FOR_PR**: 工作流继续进入 PR 创建阶段
