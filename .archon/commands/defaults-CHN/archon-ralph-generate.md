# Ralph PRD 生成器（自主模式）

**输入**: $ARGUMENTS
**工作流 ID**: $WORKFLOW_ID

---

## 你的任务

通过系统化的代码库探索与分析，生成生产级质量的 Ralph PRD 文件 — `prd.md`（完整上下文文档）和 `prd.json`（用户故事跟踪）。全程不进行交互式提问 — 基于充分信息自主做出判断。

**核心原则**：代码库优先。在编写任何内容之前先探索项目。用户故事必须引用真实文件、真实模式和真实类型。

---

## 阶段 0：检测 — 判断输入类型

| 输入模式 | 类型 | 操作 |
|---------|------|------|
| 指向 `.md` 文件且文件存在 | 已有 PRD | 读取它，从中生成 prd.json 用户故事 |
| `.archon/ralph/{slug}/prd.md` 已存在 | Ralph 目录中的已有 PRD | 在其旁边生成 prd.json |
| 自由文本 | 功能创意 | 同时生成 prd.md 和 prd.json |
| 空白/无输入 | 错误 | 停止 — 需要提供输入 |

### 若检测到已有 PRD：

1. 读取 PRD 文件
2. 提取：问题描述、目标、用户上下文、范围边界、技术需求
3. 跳转至阶段 3（技术基础）— PRD 已涵盖阶段 1-2 的内容

### 若为功能创意：

1. 保存创意描述
2. 依次完成所有阶段

## 阶段 1：理解 — 问题与上下文

**自主判断：**

1. **问题**：这解决了什么痛点？没有它会怎样？
2. **用户**：谁会受益？他们的角色和日常工作流程是什么？
3. **目标**：理想的成果是什么？如何衡量成功？
4. **范围**：最小可行产品（MVP）是什么？哪些明确不在范围内？
5. **成功指标**：哪些可衡量的信号表明这取得了成效？

基于输入描述和你对代码库的理解做出判断。

**阶段 1 检查点：**
- [ ] 问题已清晰阐述
- [ ] 目标用户已明确
- [ ] 目标与成功指标已定义
- [ ] 范围边界已设定

---

## 阶段 2：UX 与设计 — 用户旅程

**自主判断：**

1. **触发点**：什么事件导致用户需要此功能？
2. **正常路径**：从触发到成功的分步用户流程
3. **状态**：空状态、加载中、错误、成功 — 各是什么样子？
4. **边界情况**：可能出现什么问题？应如何处理？
5. **交互模式**：CLI 命令、API 端点、UI 组件？

如果该功能包含 UI 部分，描述视觉需求。
如果是纯后端功能，描述 API 接口。

**阶段 2 检查点：**
- [ ] 用户旅程已梳理
- [ ] 各状态已列举
- [ ] 边界情况已识别

## 阶段 3：技术基础 — 代码库探索

**这是关键阶段。** 使用 Task 工具配合 `subagent_type="Explore"` 系统化地探索代码库。

### 3.1 查找相似实现

```
探索代码库中与以下功能相关的模式：{功能描述}

查找：
1. 可参考的相似实现（附带 file:line 引用）
2. 需扩展或复用的已有类型/接口
3. 命名规范（函数、文件、变量）
4. 错误处理模式
5. 测试模式（框架、结构、断言风格）
6. 数据库 schema 模式（如适用）
7. 组件模式（如涉及 UI）
```

### 3.2 识别集成点

```
追踪以下功能的数据流和入口点：{功能描述}

查找：
1. 新代码与已有代码的连接位置
2. 受影响的模块/包
3. 需遵循的导入模式
4. 配置/环境变量依赖
```

### 3.3 阅读项目规则

```bash
cat CLAUDE.md
```

提取：编码规范、命名约定、测试要求、Lint 规则。

**阶段 3 检查点：**
- [ ] 已找到相似实现并附带 file:line 引用
- [ ] 类型和接口已识别
- [ ] 集成点已映射
- [ ] CLAUDE.md 规则已记录

## 阶段 4：故事拆分 — 按迭代分解

### 4.1 识别层次

将功能拆分为实现层次：

| 层次 | 示例 | 典型故事数量 |
|------|------|-------------|
| Schema/类型 | 数据库列、接口、Zod schema | 1-2 |
| 后端逻辑 | 服务、工具函数、API 端点 | 2-4 |
| UI 组件 | 新组件、修改 | 1-3 |
| 集成 | 连接、配置、导出 | 1-2 |
| 测试 | 独立的测试故事（如较复杂） | 0-2 |

### 4.2 规模规则

每个故事必须能在一次迭代（约 15-30 分钟 AI 工作）内完成：

**合适的规模（一次迭代）：**
- 添加数据库列 + 迁移
- 创建一个工具函数 + 测试
- 添加一个 UI 组件
- 更新一个 API 端点 + 测试
- 为一个功能编写集成测试

**过大（必须拆分）：**
- "构建整个功能" → 拆分为 schema、类型、后端、UI
- "添加认证" → 拆分为 schema、中间件、登录 UI、token 处理
- "重构模块" → 按文件或关注点拆分

### 4.3 依赖排序

- 故事按依赖关系排序（低优先级 = 先执行）
- Schema → 类型 → 后端 → UI → 集成
- `dependsOn` 只能引用低优先级的故事
- 校验：无循环依赖，无前向引用

### 4.4 验收标准规则

**好的标准（可验证）：**
- "添加 `priority` 列，类型为 `'high' | 'medium' | 'low'`"
- "当输入为 null 时，函数返回空数组"
- "按钮在提交时显示加载状态"
- "类型检查通过，零错误"

**差的标准（模糊）：**
- "能正确工作"
- "用户体验好"
- "处理边界情况"

每条标准都必须可通过/失败来判定。

**阶段 4 检查点：**
- [ ] 故事已按单次迭代的规模设定
- [ ] 依赖关系构成有效的 DAG（无环路）
- [ ] 所有验收标准均可验证
- [ ] 技术说明引用了真实的文件和模式

## 阶段 5：生成 — 编写 PRD 文件

### 5.1 确定功能 Slug

- "Workflow Lifecycle Overhaul" → `workflow-lifecycle-overhaul`
- "Dark Mode Toggle" → `dark-mode-toggle`
- 最多 50 个字符

### 5.2 创建目录

```bash
mkdir -p .archon/ralph/{slug}
```
