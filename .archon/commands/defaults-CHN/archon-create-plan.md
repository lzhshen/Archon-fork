# 创建实施计划

**输入**: $ARGUMENTS
**工作流 ID**: $WORKFLOW_ID

---

## 你的任务

通过系统化的代码库探索、模式提取和策略研究，将"$ARGUMENTS"转化为经过充分验证的实施计划。

**核心原则**: 仅做规划 -- 不编写代码。创建一份上下文丰富的文档，使实施能够一次成功。

**执行顺序**: 先做代码库分析，再做外部研究。方案必须先适配现有模式，再考虑引入新模式。

**智能体策略**: 使用 Task 工具并设置 subagent_type="Explore" 进行代码库情报收集，确保在外部研究之前完成全面的模式发现。

**输出**: `$ARTIFACTS_DIR/plan.md`

---

## 阶段 0: 检测 -- 输入类型判定

### 0.1 确定输入类型

| 输入模式 | 类型 | 操作 |
|----------|------|------|
| 以 `.prd.md` 结尾 | PRD 文件 | 解析 PRD，选择下一阶段 |
| 以 `.md` 结尾且包含"Implementation Phases" | PRD 文件 | 解析 PRD，选择下一阶段 |
| 存在的文件路径 | 文档 | 读取并提取功能描述 |
| 自由文本 | 描述 | 直接作为功能输入使用 |
| 空/空白 | 错误 | 停止 -- 需要输入 |

### 0.2 若检测到 PRD 文件

1. **读取 PRD 文件**
2. **解析实施阶段表格** -- 查找状态为 `Status: pending` 的行
3. **检查依赖** -- 仅选择依赖状态为 `complete` 的阶段
4. **选择下一个可执行阶段:**
   - 第一个所有依赖均已完成的待执行阶段
   - 如果有多个候选阶段具有相同依赖，记录并行执行机会

5. **提取阶段上下文:**
   ```
   阶段: {阶段编号和名称}
   目标: {来自阶段详情}
   范围: {来自阶段详情}
   成功信号: {来自阶段详情}
   PRD 上下文: {问题描述、用户、假设，来自 PRD}
   ```

6. **向用户报告选择结果:**
   ```
   PRD: {prd 文件路径}
   选中阶段: #{编号} - {名称}

   {若有可并行的阶段:}
   注意: 阶段 {X} 可以并行执行（在独立工作树中）。

   正在执行阶段 #{编号}...
   ```

### 0.3 若为自由文本描述

直接带着输入作为功能描述进入阶段 1。

**阶段 0 检查点:**

- [ ] 输入类型已确定
- [ ] 若为 PRD: 下一阶段已选择且依赖已验证
- [ ] 功能描述已为阶段 1 做好准备

```bash

# 从配置文件识别项目类型

cat go.mod 2>/dev/null | head -20
```

`src/` 的常见替代结构：
- `app/` (Next.js, Rails, Laravel)
- `lib/` (Ruby gems, Elixir)

- 根目录级源文件 (Python, scripts)

## 阶段 5: 架构 -- 策略设计

### 5.0 原语盘点

在设计方案之前，审查已有的构建模块：

1. **已存在哪些原语?** 列出代码库中与本功能相关的核心抽象 -- 附探索智能体输出的 file:line 引用。
2. **它们是否完整?** 现有原语是否覆盖本用例，还是有缺口需要扩展?
3. **先扩展再新增** -- 能否扩展现有原语而非创建新原语? 优先使用 `implements ExistingInterface` 而非 `interface NewInterface`。
4. **最小原语面** -- 如果确实需要新原语，什么是最小的、既能支持本功能又对后续调用者有用的扩展?
5. **依赖链** -- 哪些必须先存在? 本功能解锁了哪些下游能力?

| 原语 | 文件:行号 | 是否完整? | 在功能中的角色 |
|------|-----------|-----------|----------------|
| {名称} | `path/to/file.ts:10-30` | 是/部分/否 | {如何被使用或扩展} |

### 5.1 深度分析

考虑以下维度（如需要可使用扩展思维）：

- **架构适配**: 如何与现有架构集成?
- **执行顺序**: 必须先做什么 → 第二步 → 第三步?
- **失败模式**: 边界情况、竞态条件、错误场景?
- **性能**: 能否扩展? 数据库查询是否优化?
- **安全**: 攻击面? 数据泄露风险? 认证/授权?
- **可维护性**: 后续开发者能否理解这段代码?

### 5.2 记录决策

```markdown
选定方案: [描述]
理由: [为什么选择此方案而非其他 -- 引用代码库模式]

- [替代方案 1]: 否决原因 [具体理由]
- [替代方案 2]: 否决原因 [具体理由]

不在范围内 (明确的范围限制):
- [项 1 - 明确排除及原因]

```
