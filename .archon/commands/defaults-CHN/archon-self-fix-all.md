# 自动修复所有审查发现

---

## 重要提示：输出行为

**你的输出将作为 GitHub 评论发布。** 请将工作输出保持在最低限度：
- 不要逐条叙述每个步骤
- 不要输出冗长的进度更新
- 只在最后输出结构化的总结报告

---

## 你的任务

阅读所有审查产物并修复所有发现的问题。与保守的自动修复不同，你倾向于积极修复。大语言模型生成代码的速度很快 — 利用这一优势添加测试、修复文档、改进错误处理，并解决所有发现的问题。

**原则**：除非它明确是一个应单独开 issue 的不相关新问题，否则一律修复。为已有代码添加测试？修。更新文档？修。补充缺失的错误处理？修。跳过的门槛很高 — 只有当修复会引入一个真正超出 PR 范围的新功能或新关注点时才跳过。

**输出产物**：`$ARTIFACTS_DIR/review/fix-report.md`
**Git 操作**：提交并推送修复到 PR 分支
**GitHub 操作**：将修复报告作为评论发布到 PR

---

## 阶段 1：加载 — 获取上下文

### 1.1 获取 PR 编号和分支

```bash
PR_NUMBER=$(cat $ARTIFACTS_DIR/.pr-number)
HEAD_BRANCH=$(gh pr view $PR_NUMBER --json headRefName --jq '.headRefName')
echo "PR: $PR_NUMBER, Branch: $HEAD_BRANCH"
```

### 1.2 切换到 PR 分支

```bash
git fetch origin $HEAD_BRANCH
git checkout $HEAD_BRANCH
git pull origin $HEAD_BRANCH
```

验证：

```bash
git branch --show-current
git status --porcelain
```

### 1.3 阅读所有审查产物

```bash
ls $ARTIFACTS_DIR/review/
```

阅读每个包含发现问题的 `.md` 文件（例如 `code-review-findings.md`、`error-handling-findings.md`、`test-coverage-findings.md`、`comment-quality-findings.md`、`docs-impact-findings.md`、`consolidated-review.md`）。跳过 `scope.md` 和 `fix-report.md`。

```bash
for f in $ARTIFACTS_DIR/review/*.md; do
  echo "=== $f ==="; cat "$f"; echo
done
```

### 1.4 提取所有发现

汇总所有发现的统一列表，包含严重级别、位置和建议的修复方案。

**阶段 1 检查点：**

- [ ] PR 编号和分支已识别
- [ ] 已切换到正确的 PR 分支
- [ ] 所有审查产物已阅读
- [ ] 所有发现已提取

---

## 阶段 2：分类 — 决定修复内容

对每个发现，决定：**修复** 还是 **跳过**。

### 修复（默认 — 倾向于修复）：

- 真实的 bug、类型错误、静默失败、代码质量问题
- PR 变更涉及或触及的代码缺少测试
- 文档缺失或过时
- 错误处理缺失
- 注释质量问题
- 导入组织问题
- 命名改进
- 修复方案明确且代码在 PR 涉及范围内的任何发现

### 仅在以下情况跳过：

- 修复会引入与 PR 无关的**全新功能**
- 修复需要影响未涉及子系统的**架构变更**
- 发现涉及的代码与 PR 的变更**完全不相关**
- 发现内容有误或基于误解

**关键原则**：如果审查智能体在审查本 PR 时发现了问题，就可以修复。测试、文档、简化、错误处理 — 都可以修。唯一跳过的理由是"这是一个应单独开 issue 的新关注点"。

对每个跳过的发现，记录**具体原因**。

**阶段 2 检查点：**

- [ ] 每个发现已标记为修复或跳过
- [ ] 跳过原因已记录（应该很少）

---

## 阶段 3：实施 — 应用修复

### 3.1 对每个标记为修复的发现

1. 阅读相关文件
2. 按建议方案应用修复
3. 每次修复后运行类型检查：`bun run type-check`
4. 记录具体修改了什么

### 3.2 添加测试

对于任何涉及缺失测试的发现：

1. 创建或更新测试文件
2. 编写有意义的测试（不是桩代码）
3. 运行测试：`bun test {file}`

### 3.3 修复文档

对于任何涉及文档的发现：

1. 更新相关文档
2. 确保与当前代码一致

### 3.4 处理受阻的修复

如果某个修复无法应用（审查时代码已变更、修复会破坏其他功能），标记为**受阻**并注明原因。不要强行应用有问题的修复。

**阶段 3 检查点：**

- [ ] 所有标记为修复的发现已尝试处理
- [ ] 已标记的地方已添加测试
- [ ] 已标记的地方已更新文档
- [ ] 受阻的发现已记录

---

## 阶段 4：验证 — 全面检查

```bash
bun run type-check
bun run lint
bun test
```

全部必须通过。如果修复后某项失败：

1. 查看错误信息
2. 调整修复或回退并标记为受阻
3. 重新运行直到全部通过

**阶段 4 检查点：**

- [ ] 类型检查通过
- [ ] Lint 通过
- [ ] 测试通过

---

## 阶段 5：提交并推送

### 5.1 暂存并提交

只暂存你实际修改的文件：

```bash
git add {具体文件}
git status
git commit -m "$(cat <<'EOF'
fix: address review findings

Fixed:
- {修复列表简述}

Tests added:
- {添加的测试列表简述，如有}

Skipped:
- {跳过列表简述及原因，如有}
EOF
)"
```

### 5.2 推送

```bash
git push origin $HEAD_BRANCH
```

如果推送因分叉而失败：

```bash
git pull --rebase origin $HEAD_BRANCH
git push origin $HEAD_BRANCH
```

**阶段 5 检查点：**

- [ ] 变更已提交
- [ ] 已推送到 PR 分支

## 成功标准

- **在正确的分支上**：工作在 PR 的 head 分支上进行
- **所有发现已处理**：每个发现要么已修复、要么已跳过（附原因）、要么已标记受阻（附原因）
- **积极修复**：大部分发现已修复 — 跳过率应很低
- **测试已添加**：缺失的测试覆盖已补充
- **文档已更新**：文档缺失已填补
- **验证通过**：类型检查、Lint 和测试全部通过
- **已提交并推送**：变更已提交并推送到 PR 分支
- **已报告**：修复报告产物已写入，GitHub 评论已发布
